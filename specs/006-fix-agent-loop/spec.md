# Feature Specification: Fix Agent Loop in RAG Pipeline

**Feature Branch**: `006-fix-agent-loop`
**Created**: 2026-02-27
**Status**: Draft
**Input**: User description: "Исследовать и устранить потенциальное зацикливание RAG-агента, при котором цикл план -> поиск -> ответ повторяется многократно вместо возврата финального ответа пользователю"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Agent returns answer after single tool call (Priority: P1)

Пользователь задаёт вопрос RAG-агенту. Агент вызывает инструмент поиска один раз, получает данные и сразу формирует финальный ответ пользователю без повторного вызова инструмента.

**Why this priority**: Это основной сценарий работы агента. Зацикливание приводит к многократному выполнению тяжёлого RAG-пайплайна (5-15 сек на цикл, множество LLM-вызовов), расходу токенов и блокировке пользователя без ответа.

**Independent Test**: Отправить любой портфолио-вопрос (например, "Какие проекты есть?") и убедиться, что в логах инструмент `portfolio_rag_tool` вызывается ровно один раз, после чего возвращается ответ.

**Acceptance Scenarios**:

1. **Given** пользователь отправил вопрос о портфолио, **When** агент обработал вопрос, **Then** инструмент `portfolio_rag_tool` вызван не более одного раза и ответ доставлен пользователю
2. **Given** пользователь отправил вопрос и инструмент вернул данные с высокой уверенностью, **When** агент получил результат инструмента, **Then** агент немедленно возвращает ответ без повторного вызова инструмента
3. **Given** пользователь отправил вопрос и инструмент вернул данные с низкой уверенностью, **When** агент получил результат инструмента, **Then** агент всё равно возвращает ответ (возможно, с оговоркой о неполноте), а не вызывает инструмент повторно

---

### User Story 2 - Graceful termination on unexpected re-invocation (Priority: P2)

Даже если LLM по какой-то причине решит вызвать инструмент повторно, система должна быстро и корректно завершить выполнение с понятным ответом, а не зависать на многократных циклах.

**Why this priority**: Защитный механизм на случай, если основное исправление (P1) не полностью предотвратит повторные вызовы. LLM — вероятностная система, 100% гарантии нет.

**Independent Test**: Искусственно снизить recursion_limit до минимума и проверить, что при срабатывании лимита пользователь получает понятное сообщение об ошибке, а не технический стектрейс.

**Acceptance Scenarios**:

1. **Given** агент вызвал инструмент повторно, **When** сработал лимит рекурсии, **Then** пользователь получает корректное сообщение (не технический стектрейс) и запрос завершается
2. **Given** обработка запроса затянулась, **When** превышен лимит времени выполнения, **Then** запрос прерывается и пользователь получает понятное сообщение

---

### User Story 3 - Minimal tool output to LLM (Priority: P3)

Результат инструмента, возвращаемый обратно в LLM для принятия решения, должен быть компактным и содержать только финальный ответ без сырых данных, чтобы минимизировать вероятность того, что LLM интерпретирует сырые данные как "необработанную информацию" и вызовет инструмент повторно.

**Why this priority**: Уменьшает вероятность зацикливания за счёт снижения когнитивной нагрузки на LLM. Также сокращает расход токенов.

**Independent Test**: Проверить, что в tool_result, возвращаемом агенту, отсутствуют объёмные сырые данные — присутствует только ответ и минимальные метаданные.

**Acceptance Scenarios**:

1. **Given** инструмент завершил обработку, **When** результат возвращается агенту, **Then** результат содержит только финальный ответ и флаг наличия данных, без сырых данных (полные списки фактов, детальные источники и т.д.)

---

### Edge Cases

- Что происходит при пустом ответе от генератора ответа (answer = "")?
- Что происходит при found=false в результате инструмента — может ли это спровоцировать повторный вызов?
- Как ведёт себя система при накоплении длинной истории сообщений через механизм хранения состояния (многоходовый диалог)?
- Что происходит при таймауте LLM-провайдера внутри инструмента?

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Системный промпт агента MUST содержать явную инструкцию вызывать инструмент поиска не более одного раза на каждый вопрос пользователя и после получения результата — сразу отвечать пользователю
- **FR-002**: Результат инструмента, передаваемый обратно для принятия решения, MUST содержать только два поля: `answer` (текст ответа) и `found` (флаг наличия данных). Все остальные поля (`rendered_facts`, `items`, `sources`, `confidence`, `intents`, `warnings`, `grounded`, `usage`) MUST быть исключены
- **FR-003**: Лимит рекурсии агента MUST быть снижен с 8 до 6 (нормальный путь: 5 шагов + 1 запас; при любом повторном вызове инструмента — немедленная ошибка с понятным сообщением)
- **FR-004**: Система MUST иметь таймаут на выполнение агента в 90 секунд, прерывающий обработку при превышении этого времени
- **FR-005**: При срабатывании лимита рекурсии или таймаута система MUST возвращать пользователю понятное сообщение, а не технический стектрейс или необработанную ошибку

### Key Entities

- **AgentState**: Состояние графа агента (сообщения, текущее действие, определённый маршрут)
- **ToolResult**: Результат выполнения инструмента поиска, возвращаемый для принятия решения о следующем шаге
- **RecursionLimit**: Максимальное количество шагов в графе агента, ограничивающее количество циклов
- **ExecutionTimeout**: Максимальное время обработки одного запроса агентом

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Инструмент поиска по портфолио вызывается ровно 1 раз на каждый пользовательский вопрос в 99%+ случаев
- **SC-002**: Время обработки одного запроса агентом не превышает установленного лимита, даже при аномальном поведении LLM
- **SC-003**: При срабатывании любого защитного механизма пользователь получает понятное сообщение в 100% случаев
- **SC-004**: Объём данных в результате инструмента, возвращаемом для принятия решения, сокращён минимум вдвое за счёт удаления сырых данных

## Clarifications

### Session 2026-02-28

- Q: Какие поля оставить в tool_result для Agent LLM? → A: Только `answer` + `found` — минимум, достаточный для стриминга и обработки "не найдено"
- Q: Какое значение recursion_limit установить? → A: 6 — нормальный путь (5 шагов) + 1 запас; при повторе — быстрая ошибка вместо бесполезного ожидания
- Q: Какой таймаут на выполнение агента? → A: 90 секунд — максимально мягкий, защита от бесконечного зависания без обрезки медленных провайдеров

## Assumptions

- Зацикливание вызвано тем, что ReAct-агент по дизайну передаёт результат инструмента обратно в LLM, и LLM принимает решение — вызвать инструмент снова или ответить пользователю
- LLM (в роли агента) может интерпретировать большой структурированный результат с сырыми данными как "необработанную информацию" и вызвать инструмент повторно
- Текущий системный промпт агента не содержит явного запрета на повторный вызов инструмента
- Конфигурация `return_direct=False` НЕ подлежит изменению — Agent LLM обеспечивает стриминг ответа пользователю (без него ответ придёт одним блоком без анимации). Это архитектурное ограничение, не баг
- Текущий лимит рекурсии (8) позволяет до 2 полных циклов + ошибку на 3-м; будет снижен до 6 (1 цикл + быстрая ошибка при повторе)
- Critic и Grounding Verifier не являются причиной зацикливания — они однопроходные
- MemorySaver накапливает историю вызовов инструментов между запросами в рамках сессии, что увеличивает контекст LLM

## Research Findings

### Архитектура ReAct-петли

Функция `create_agent()` из LangGraph создаёт стандартный ReAct-граф: `model -> tools -> model -> tools -> ...`. Выход из петли возможен ТОЛЬКО когда LLM генерирует сообщение без `tool_calls`. Это — единственное условие выхода. Инструмент настроен с `return_direct=False`, что означает — результат всегда возвращается в LLM для принятия решения.

### Текущее состояние tool_result

При детерминистическом ответе (контакты, публикации, project_details, technology_usage) сырые данные уже очищаются (`rag_tool.py:376-382`). Но при LLM-ответе обратно в агент возвращаются все поля: `answer`, `rendered_facts`, `items`, `sources`, `confidence`, `found`, `intents`, `warnings`, `grounded`, `usage` — это большой JSON, который LLM может интерпретировать как "необработанные данные".

### Системный промпт

Содержит инструкцию "ОБЯЗАТЕЛЬНО вызывай portfolio_rag_tool для всех вопросов о портфолио" и "поле answer — это ФИНАЛЬНЫЙ ответ, верни его КАК ЕСТЬ". Но НЕ содержит явного запрета на повторный вызов, что создаёт зазор для неоднозначной интерпретации.

### Recursion limit

Установлен в `chat.py:170` как `recursion_limit=8`. При бюджете шагов: router(1) + model(2) + tools(3) + model(4) = 4 шага на один вызов, recursion_limit=8 позволяет до 3 полных циклов RAG-пайплайна. Каждый цикл — это 5-15 секунд и множество LLM-вызовов.

### Отсутствие таймаута

В текущей реализации нет таймаута на выполнение агента. При медленных LLM-провайдерах и множественных циклах запрос может выполняться неопределённо долго.

### Что НЕ является причиной

- **Critic**: только решает, нужен ли дополнительный hybrid search — однопроходно, не вызывает re-planning
- **Grounding Verifier**: только модифицирует текст ответа (rewrite/refuse), не вызывает повторный поиск
- **Answer LLM recovery**: однопроходный fallback на детерминистический рендеринг, не создаёт петлю
